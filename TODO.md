# Отложенные задачи

Здесь собрано то, что осознанно отложено: известные ограничения, решения «в
этой итерации не делаем» и проверки, которые не удалось выполнить. Пункт
попадает сюда, когда понятен следующий шаг, но работа не входит в текущую
задачу; после закрытия пункт удаляется. Заметки о локальном тестовом окружении
в репозиторий не попадают — см. `TODO.local.md` (в git игнорируется).

## Отложено (сознательно)

Что решено не делать в текущей итерации. Формат — пункт и причина в одну
строку; где есть конкретный следующий шаг, он разобран в подразделе.

- **TLS/reverse-proxy для панели** — встроенного TLS нет, `PANEL_TLS=yes`
  переключает только ожидаемую схему в CSRF-проверке (см. «TLS для панели»).
- **Multi-worker панели** — состояние заданий, кэш `/api/status` и лимиты
  живут в памяти процесса; юнит считает `MemoryMax=256M`, воркер ровно один.
- **fake-ip в `TS_EXIT_MODE=nat`** — fake-ip реализован только в `policy`; в
  `nat` DNS и трафик tailnet идут напрямую в WAN (NET-08).
- **`DOCKER-USER` для публикации `1443`** — порт публикуется на `${SERVER_IP}`,
  а правила Docker в `DOCKER-USER` Routeweave не трогает.
- **Автоматический rollback при сбое установки** — есть бэкапы `.env` и
  `config.yaml`, копии чужих юнитов и маркер `owned`, но откат выполняется
  вручную: `uninstall.sh` и `stop` у firewall-скриптов.
- **Фильтрация IPv6** — проект IPv4-only, `ip6tables` не трогается; IPv6 в LAN
  нужно отключать, tailnet-адреса `100.x.y.z` тоже только IPv4.
- **`pip install --require-hashes`** — версии в `panel/requirements.txt`
  запинены, хешей нет (см. «`--require-hashes` для
  `panel/requirements.txt`»).
- **mypy/статическая типизация** — `make lint` ограничен `bash -n`,
  shellcheck, ruff и `compileall`.
- **JS DOM-тесты панели** — правки `app.js` проверяются статически
  (`tests/test_panel.py` ищет строки и запрещённые API), DOM не исполняется.
- **Построчный парсер вместо `source` в firewall-скриптах** — `.env` и
  `zapret.conf` по-прежнему читаются через `.` (см. «`source` `.env` и
  `zapret.conf` в firewall-скриптах»).
- **Легаси `wg+` в `FORWARD`** — на старых установках правило остаётся, но
  перекрыто прыжком в `ROUTEWEAVE-FWD` (см. «Легаси `wg+` в цепочке
  `FORWARD`»).
- **Fingerprint/проверка Tailscale auth-key** — ключ передаётся в `tailscale up`
  как есть (`--auth-key=file:...` либо временный файл `0600`), его отпечаток и
  принадлежность не сверяются.

### TLS для панели

Панель использует Basic-авторизацию, и по HTTP логин с паролем передаются
открытым текстом. В домашней LAN с чужими устройствами (гости, IoT,
скомпрометированный клиент) их снимает сниффер; вместе с паролем видны токены и
содержимое страниц. Риск — полный доступ к панели, а через неё к управлению
сервисами по sudo-allowlist. Что сделать: reverse-proxy с TLS (Caddy или nginx)
перед панелью либо встроенный TLS; сертификат — локальный CA или Let's Encrypt с
DNS-01. Это отдельная работа: затрагивает установщик, README и проверку
`Origin`/CSRF.

### `--require-hashes` для `panel/requirements.txt`

Версии зависимостей запинены, установка идёт с PyPI по HTTPS, поэтому риск
подмены пакета низкий. Полноценная защита от подмены в индексе или
компрометации зеркала — хеши в requirements. Что сделать: сгенерировать
`pip-compile --generate-hashes` (pip-tools), перевести установщик и CI на
`pip install --require-hashes` и договориться, как обновлять хеши.

### `source` `.env` и `zapret.conf` в firewall-скриптах

`fw-base.sh`, `fw-wan.sh`, `fw-nfq.sh` и `fw-tailscale.sh` читают конфигурацию
через `.` (source): первые три — `.env`, `fw-nfq.sh` — ещё и `zapret.conf`.
Файлы принадлежат root и на запись доступны только ему: `.env` —
`0640 root:routeweave`, `zapret.conf` — `0600 root`. Для эксплуатации уже нужен
root; риск — случайное выполнение кода при компрометации файла или ошибке в
правах. Что сделать: заменить source на аккуратный парсер нужных переменных (как
`env_get` в `routeweave-update-lists.sh`) либо явно валидировать файлы перед
чтением.

### Легаси `wg+` в цепочке `FORWARD`

На старых установках в `FORWARD` остаётся правило с шаблоном `wg+`. Сейчас
трафик перекрывается прыжком в `ROUTEWEAVE-FWD`, который стоит выше, поэтому
дыры это правило не создаёт, но это мусор и лишний источник путаницы при
разборе. Что сделать: при следующей правке firewall добавить в `fw-base.sh`
снятие известных легаси-правил, убедившись, что VPN-интерфейсы (`wg*`, `wdtt0`)
обрабатываются текущими правилами; `tailscale0` уже добавлен в `fw-base.sh`
вместе с exit node.

## Не проверено на живом стенде

По итогам прогона установщика на тестовой VM (Ubuntu 26.04.1) осталось
непроверенным:

- UFW — на стенде был inactive, поэтому ветка добавления правил не
  выполнялась; нужен прогон с `ufw enable` и проверка `ufw status numbered`.
- WDTT-Plus (`INSTALL_WDTT=yes`) — установка и вход с Android-клиента.
- Установка Tailscale через `INSTALL_TAILSCALE=yes` и авторизация по ключу
  (`TS_AUTHKEY_FILE`/`TS_AUTHKEY`) — на VM и живом tailnet не проверялись.
- tg-ws-proxy (docker, `INSTALL_TGWS=yes`) — запуск контейнера и подключение
  Telegram.
- `WAN_INGRESS=yes` — доступ снаружи, цепочка `ROUTEWEAVE-WANMARK`, connmark и
  `ip rule` priority 8993.
- Реальный трафик LAN-клиентов и DPI-обход — проверялись только косвенные
  признаки; нужен клиент за шлюзом и сайты из списков.
- Срабатывание `routeweave-lists-update.timer` в 04:15 — таймер установлен, но
  фактический запуск по расписанию не дожидались.
- zashboard UI в браузере — проверены только HTTP 200 и CSP; нужен визуальный
  прогон SPA и запросов к API mihomo.
- Проверка целостности загрузок: `verify_sha` и закреплённые суммы покрыты
  тестами `tests/test_supply_chain.py`, но прогон установки с заведомо
  несовпавшей суммой и с `--allow-unverified` на стенде не выполнялся.

В тот прогон не входила проверка Tailscale exit node на живом tailnet:
одобрение узла в admin console, DNS/fake-ip через `100.x.y.z`, доступ к
панели/zashboard/DNS/прокси по tailscale-адресу, правила ufw для `tailscale0`
и `100.64.0.0/10`.

## Известные мелочи

- `fw-nfq.sh`: `start` не убирает NFQUEUE-правила прежних форм (другой набор
  портов/UDP), поэтому при обновлении с нестандартной конфигурации в
  `POSTROUTING` остаются дубли и пакеты уходят в очередь дважды. Что сделать:
  перед добавлением правила снимать все правила `POSTROUTING` с нашим
  `--queue-num`, плюс тест.
