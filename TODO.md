# Отложенные задачи

Здесь собрано то, что осознанно отложено: известные ограничения и проверки,
которые не удалось выполнить. Пункт попадает сюда, когда понятен следующий шаг,

локальном тестовом окружении в репозиторий не попадают — см. `TODO.local.md`

## Безопасность

### TLS для панели

Панель использует Basic-авторизацию, и по HTTP логин с паролем передаются
открытым текстом. В домашней LAN с чужими устройствами (гости, IoT,
скомпрометированный клиент) их снимает сниффер; вместе с паролем видны токены и
содержимое страниц. Риск — полный доступ к панели, а через неё к управлению
сервисами по sudo-allowlist. Что сделать: reverse-proxy с TLS (Caddy или nginx)
перед панелью либо встроенный TLS; сертификат — локальный CA или Let's Encrypt с
DNS-01. Это отдельная работа: затрагивает установщик, README и проверку
`Origin`/CSRF.

### `--require-hashes` для `panel/requirements.txt`

Версии зависимостей запинены, установка идёт с PyPI по HTTPS, поэтому риск
подмены пакета низкий. Полноценная защита от подмены в индексе или
компрометации зеркала — хеши в requirements. Что сделать: сгенерировать
`pip-compile --generate-hashes` (pip-tools), перевести установщик и CI на
`pip install --require-hashes` и договориться, как обновлять хеши.

### shell-source `.env` и `zapret.conf` в firewall-скриптах

`fw-base.sh`, `fw-nfq.sh` и `fw-wan.sh` читают конфигурацию через `.` (source).
Файлы root-only (`0640`, панель их не пишет), поэтому для эксплуатации нужно уже
иметь root. Риск — случайное выполнение кода при компрометации файла или ошибке
в правах. Что сделать: заменить source на аккуратный парсер нужных переменных
(как в `routeweave-update-lists.sh`) либо явно валидировать файлы перед чтением.

### Легаси `wg+` в цепочке `FORWARD`

На старых установках в `FORWARD` остаётся правило с шаблоном `wg+`. Сейчас
трафик перекрывается прыжком в `ROUTEWEAVE-FWD`, который стоит выше, поэтому
дыры это правило не создаёт, но это мусор и лишний источник путаницы при
разборе. Что сделать: при следующей правке firewall добавить в `fw-base.sh`
снятие известных легаси-правил, убедившись, что VPN-интерфейсы (`wg*`, `wdtt0`)
обрабатываются текущими правилами; `tailscale0` уже добавлен в `fw-base.sh`
вместе с exit node.

## Отложенные функции

### Tailscale: NAT и IPv6

Базовый вход `tailscale0` и режим exit node сделаны: forwarding в TUN,
возвратный путь, CGNAT-спуф-гард, `ip rule` 8991, диагностика
`fw-tailscale.sh status|doctor` и ufw-правила для прямых соединений и
tailnet-портов. Автоустановка (`INSTALL_TAILSCALE=yes`) сделана. Сделана и
карточка Tailscale в панели: статус `tailscaled`, tailnet-адрес, флаги exit
node, трафик и число пиров. Отложено:

- прямой NAT-режим для exit node, без заворота в TUN mihomo; сейчас доступен
  только policy-режим.
- IPv6: проект IPv4-only, tailnet-адреса `100.x.y.z` — только IPv4.

## Не проверено на живом стенде

По итогам прогона установщика на тестовой VM (Ubuntu 26.04.1) осталось
непроверенным:

- UFW — на стенде был inactive, поэтому ветка добавления правил не
  выполнялась; нужен прогон с `ufw enable` и проверка `ufw status numbered`.
- WDTT-Plus (`INSTALL_WDTT=yes`) — установка и вход с Android-клиента.
- Установка Tailscale через `INSTALL_TAILSCALE=yes` и авторизация по ключу
  (`TS_AUTHKEY_FILE`/`TS_AUTHKEY`) — на VM и живом tailnet не проверялись.
- tg-ws-proxy (docker, `INSTALL_TGWS=yes`) — запуск контейнера и подключение
  Telegram.
- `WAN_INGRESS=yes` — доступ снаружи, цепочка `ROUTEWEAVE-WANMARK`, connmark и
  `ip rule` priority 8993.
- Реальный трафик LAN-клиентов и DPI-обход — проверялись только косвенные
  признаки; нужен клиент за шлюзом и сайты из списков.
- Срабатывание `routeweave-lists-update.timer` в 04:15 — таймер установлен, но
  фактический запуск по расписанию не дожидались.
- SHA-проверка загрузок mihomo/zashboard — upstream не отдаёт `.sha256`,
  поэтому проверка уходила в ветку предупреждения; нужен прогон с
  закреплёнными суммами.
- zashboard UI в браузере — проверены только HTTP 200 и CSP; нужен визуальный
  прогон SPA и запросов к API mihomo.

В тот прогон не входила проверка Tailscale exit node на живом tailnet:
одобрение узла в admin console, DNS/fake-ip через `100.x.y.z`, доступ к
панели/zashboard/DNS/прокси по tailscale-адресу, правила ufw для `tailscale0`
и `100.64.0.0/10`.

## Известные мелочи

- `install.sh` не перезапускает уже активные сервисы: `enable --now` на
  работающем юните не перечитывает новый код. После обновления кода нужен
  ручной `systemctl restart routeweave-firewall routeweave-panel`
  (либо `try-restart` в установщике).
- `mihomo` перезапускается только вручную: новый `ExecStartPost` в юните
  вступит в силу при следующем рестарте, установщик сам его не делает.
- `fw-nfq.sh`: `start` не убирает NFQUEUE-правила прежних форм (другой набор
  портов/UDP), поэтому при обновлении с нестандартной конфигурации в
  `POSTROUTING` остаются дубли и пакеты уходят в очередь дважды. Что сделать:
  перед добавлением правила снимать все правила `POSTROUTING` с нашим
  `--queue-num`, плюс тест.
