# Политика безопасности Routeweave

Routeweave — домашний шлюз, который по своей природе работает с сетевым
трафиком и привилегированными сервисами. Ниже описано, что считается
поддерживаемым, как сообщить об уязвимости и какие ограничения заложены
в архитектуру осознанно.

## Поддерживаемые версии

| Версия | Поддержка |
|---|---|
| `main` | да, исправления выходят в `main` |
| форки и старые снимки | нет, поддерживаются владельцем форка |

Исправления безопасности не выпускаются отдельными ветками: актуальным
считается последний `main`.

## Как сообщить об уязвимости

**Не открывайте публичный issue** с деталями уязвимости.

Используйте приватный канал GitHub Security Advisories в репозитории
(вкладка **Security → Advisories → Report a vulnerability**) либо свяжитесь
с владельцем репозитория приватно. Публичное обсуждение — только после
исправления и по согласованию.

В сообщении полезно указать:

- коммит или версию Routeweave (`git rev-parse HEAD`);
- шаги воспроизведения и ожидаемое/фактическое поведение;
- влияние: что именно получает атакующий (чтение файлов, команды, обход
  маршрутизации, отказ в обслуживании);
- минимальный PoC и релевантные фрагменты конфигурации **без секретов**.

Не присылайте настоящие `PANEL_PASS`, `MIHOMO_SECRET`, `TG_SECRET`,
содержимое `/etc/routeweave/.env` и приватные ключи. Для демонстрации
замените их заглушками.

## Модель угроз

### Веб-панель

- Панель предназначена для **доверенной локальной сети**. Её нельзя
  выставлять в интернет напрямую.
- Если доступ снаружи действительно нужен, ставьте панель за
  reverse-proxy с TLS (Caddy или nginx) на отдельном хосте либо открывайте
  её только через VPN. Проброс `PANEL_PORT` из интернета не поддерживается.
- Basic-авторизация без TLS передаёт логин и пароль в открытом виде по LAN.
  Это известное ограничение, а не скрытая функция: используйте TLS на
  reverse-proxy, если в сети есть недоверенные устройства.
- Панель работает от системного пользователя `routeweave`, а не от root.
  Все привилегированные операции выполняются через `sudo -n` строго по
  allowlist из `/etc/sudoers.d/routeweave-panel`: перезапуск конкретных
  юнитов и три helper-скрипта, без wildcard и без произвольных команд.
- В юните панели осознанно стоит `NoNewPrivileges=no`: иначе setuid-`sudo`
  не сможет повысить привилегии и кнопки перезапуска перестанут работать.
  Компенсация — пустой `CapabilityBoundingSet`, `ProtectSystem=strict`,
  `ProtectHome`, `PrivateTmp`, `RestrictAddressFamilies` и sudo-allowlist.
- Изменяющие запросы защищены от CSRF: проверяются `Origin`, `Referer` и
  `Sec-Fetch-Site`. Ответы отдаются с CSP без inline-скриптов и стилей и
  security-заголовками; статика вынесена в `app.css`/`app.js`, `innerHTML`
  не используется.
- Списки доменов пишутся атомарно (временный файл + `rename`), домены
  валидируются, размер загрузки ограничен.

### Секреты и файлы конфигурации

- `/etc/routeweave/.env` — `0640 root:routeweave`: читать могут только root
  и сервисный пользователь панели. В файле лежат `PANEL_PASS`,
  `MIHOMO_SECRET`, `TG_SECRET` и параметры прокси.
- `/etc/routeweave/.env.tgws` — `0640 root:root`, содержит только
  `TG_SECRET`, `BASE_DOMAIN` и `TG_CF_WORKER_DOMAIN`. Контейнер tg-ws-proxy
  получает только эти три переменные и не видит секретов панели и mihomo.
- Установщик не печатает секреты в консоль (кроме сгенерированного
  `PANEL_PASS` в итоговой сводке — его нужно передать пользователю).
- Панель не отдаёт `.env` и не логирует его содержимое.

### Firewall и маршрутизация

- Правила живут в отдельной цепочке `ROUTEWEAVE-FWD`, из `FORWARD` в неё
  ведёт ровно один прыжок. Это исключает конфликты позиций с docker/ufw.
- `DROP UDP/443` (`QUIC_DROP=yes`) стоит **выше** разрешающих правил,
  иначе QUIC у VPN-клиентов не режется.
- `ip rule` priority 8990 направляет `WG_SUBNET` в таблицу маршрутизации
  Routeweave; VPN-интерфейсы (`wdtt0`, `tailscale0`, существующие `wg*`)
  получают ту же политику, что LAN.
- Наружу не пробрасываются `53`, `7890`, `9090`, `PANEL_PORT` и `1443`.
  Исключение — `56000/udp` для WDTT-Plus, он предназначен для внешнего
  доступа.

### Целостность загрузок

- mihomo и zashboard проверяются по sha256, если апстрим публикует
  `<url>.sha256`; ожидаемую сумму можно задать через `MIHOMO_SHA256` и
  `ZASHBOARD_SHA256`.
- Если контрольная сумма недоступна, установщик громко предупреждает, что
  целостность не проверена. Это предупреждение, а не гарантия.
- Коммит zapret фиксируется в `/etc/routeweave/zapret.commit` для
  воспроизводимости.

## Что не является уязвимостью

- Необходимость root для установки, изменения firewall и DNS.
- Доступ к панели по HTTP из доверенной LAN, если TLS не настроен: это
  известное ограничение с рекомендацией использовать reverse-proxy с TLS.
- Срезание QUIC при `QUIC_DROP=yes` и откат приложений на TCP — штатное
  поведение.
- Отсутствие защиты от пользователя, который уже является root на шлюзе:
  он по определению контролирует систему.
- Срабатывание предупреждения об отсутствии sha256 у апстрима — это
  прозрачность, а не дефект.

## Ответственное раскрытие

Мы придерживаемся скоординированного раскрытия: 90 дней с момента
подтверждения отчёта либо иной срок по согласованию, если исправление
требует сложных изменений. Пожалуйста, не публикуйте детали и PoC до
выхода исправления. Указание автора в благодарностях — по желанию.
