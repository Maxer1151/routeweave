# Политика безопасности Routeweave

Routeweave — домашний шлюз, который по своей природе работает с сетевым
трафиком и привилегированными сервисами. Ниже описано, что считается
поддерживаемым, как сообщить об уязвимости и какие ограничения заложены
в архитектуру осознанно.

## Поддерживаемые версии

| Версия | Поддержка |
|---|---|
| `main` | да, исправления выходят в `main` |
| форки и старые снимки | нет, поддерживаются владельцем форка |

Исправления безопасности не выпускаются отдельными ветками: актуальным
считается последний `main`.

## Как сообщить об уязвимости

**Не открывайте публичный issue** с деталями уязвимости.

Используйте приватный канал GitHub Security Advisories в репозитории
(вкладка **Security → Advisories → Report a vulnerability**) либо свяжитесь
с владельцем репозитория приватно. Публичное обсуждение — только после
исправления и по согласованию.

В сообщении полезно указать:

- коммит или версию Routeweave (`git rev-parse HEAD`);
- шаги воспроизведения и ожидаемое/фактическое поведение;
- влияние: что именно получает атакующий (чтение файлов, команды, обход
  маршрутизации, отказ в обслуживании);
- минимальный PoC и релевантные фрагменты конфигурации **без секретов**.

Не присылайте настоящие `PANEL_PASS`, `MIHOMO_SECRET`, `TG_SECRET`,
содержимое `/etc/routeweave/.env` и приватные ключи. Для демонстрации
замените их заглушками.

## Модель угроз

### Веб-панель

- Панель предназначена для **доверенной локальной сети**. Её нельзя
  выставлять в интернет напрямую.
- Если доступ снаружи действительно нужен, ставьте панель за
  reverse-proxy с TLS (Caddy или nginx) на отдельном хосте либо открывайте
  её только через VPN. Проброс `PANEL_PORT` из интернета не поддерживается.
- Basic-авторизация без TLS передаёт логин и пароль в открытом виде по LAN.
  Это известное ограничение, а не скрытая функция: используйте TLS на
  reverse-proxy, если в сети есть недоверенные устройства.
- Панель работает от системного пользователя `routeweave`, а не от root.
  Все привилегированные операции выполняются через `sudo -n` строго по
  allowlist из `/etc/sudoers.d/routeweave-panel`: перезапуск конкретных
  юнитов и четыре helper-скрипта, без wildcard и без произвольных команд.
- Helper `routeweave-tailscale-state.sh` только читает состояние Tailscale
  (`systemctl is-active`, `tailscale status --json`, счётчики sysfs) и
  возвращает агрегаты — статус, tailnet-адрес, флаги exit node, счётчики и
  число пиров — без ключей, имён устройств и списка пиров.
- В юните панели осознанно стоит `NoNewPrivileges=no`: иначе setuid-`sudo`
  не сможет повысить привилегии и кнопки перезапуска перестанут работать.
  `CapabilityBoundingSet` при этом не пустой: в нём минимальный набор
  `CAP_SETUID CAP_SETGID CAP_CHOWN CAP_DAC_OVERRIDE CAP_DAC_READ_SEARCH
  CAP_FOWNER CAP_KILL CAP_AUDIT_WRITE CAP_SYS_CHROOT`, потому что setuid-root
  `sudo` при пустом bounding set падает с «unable to set groups» и не может
  выполнить разрешённые команды. Широких capability (`CAP_SYS_ADMIN`,
  `CAP_NET_ADMIN`, `CAP_SYS_PTRACE`) в наборе нет; остальные ограничения —
  `ProtectSystem=strict`, `ProtectHome`, `PrivateTmp`,
  `RestrictAddressFamilies` и sudo-allowlist — остаются в силе.
- Изменяющие запросы защищены fail-closed: нужен совпадающий `Origin`/`Referer`,
  либо `Sec-Fetch-Site: same-origin|none`, либо `X-Requested-With: Routeweave`
  (запасной путь для не-браузерных клиентов). Если заголовок есть, но не
  совпадает, — `403`, без «тихого» пропуска. `Host` проверяется по allowlist до
  Basic-auth: неизвестный `Host` получает `421`; пустой
  `PANEL_ALLOWED_HOSTS` не означает «любые» — базовый набор всегда ограничен.
- Лимиты: `PANEL_RATE_LIMIT` по IP (`120/60` по умолчанию) и отдельный
  `PANEL_AUTH_RATE_LIMIT` на неуспешный Basic-auth (`10/60`); превышение —
  `429`. Тело списка больше 200 КБ отклоняется с `413` и читается потоком,
  поэтому chunked-передача не обходит лимит. `/api/status` кэшируется на 3 с и
  использует single-flight; переполнение одновременных запросов — `429`.
- Ответы отдаются с security-заголовками; статика вынесена в
  `app.css`/`app.js`, `innerHTML` не используется. CSP панели строгая:
  `script-src 'self'`, `frame-ancestors 'none'`, `object-src 'none'`,
  inline-скрипты и стили запрещены; дополнительно отдаются `Permissions-Policy`,
  COOP и CORP. Zashboard панель не раздаёт: его отдаёт mihomo на отдельном
  origin `http://SERVER_IP:9090/ui/`, поэтому CSP панели на него не действует.
- Списки доменов пишутся атомарно (временный файл + `rename`), домены
  валидируются по меткам (дефис на краю метки отклоняется), размер загрузки
  ограничен.

### Секреты и файлы конфигурации

- `/etc/routeweave/.env` — `0640 root:routeweave`: читать могут только root
  и сервисный пользователь панели. В файле лежат `PANEL_PASS`,
  `MIHOMO_SECRET`, `TG_SECRET` и параметры прокси.
- `.env` — данные, а не shell-скрипт. Значения записываются в одинарных
  кавычках (`KEY='value'`, апостроф — `'\''`); `install.sh`, апдейтер списков и
  панель разбирают файл построчным парсером, `source`/`eval` в установщике и
  апдейтере не используются. В этих компонентах `$(...)`, обратные кавычки и
  `;` внутри значения не исполняются. Firewall-скрипты по-прежнему читают
  `.env` через `source` — файл принадлежит root и недоступен на запись
  непривилегированным пользователям.
- При повторной установке создаётся бэкап `.env.bak.YYYYmmdd-HHMMSS`
  (`0600 root:root`), затем управляемые ключи обновляются (upsert). Чужие
  ключи и комментарии сохраняются.
- `/etc/routeweave/.env.tgws` — `0640 root:root`, содержит `TG_SECRET`,
  `BASE_DOMAIN`, `TG_CF_WORKER_DOMAIN` и (если задан) `TG_PINNED_UPSTREAM`.
  Контейнер tg-ws-proxy получает только эти переменные и не видит секретов
  панели и mihomo. Пустой `TG_PINNED_UPSTREAM` в файл не пишется: пустой
  список тиров для прокси невалиден.
- Установщик не печатает секреты в консоль, кроме сгенерированного
  `PANEL_PASS` в итоговой сводке — и только когда stdout является терминалом
  (TTY) и пароль действительно сгенерирован. При `| tee`, редиректе в лог или
  запуске из CI пароля в выводе нет, вместо него — отсылка к
  `/etc/routeweave/.env` → `PANEL_PASS`. `MIHOMO_SECRET`, `TG_SECRET` и
  `SOCKS_URL` в сводку не попадают.
- Панель не отдаёт `.env` и не логирует его содержимое.

### Docker и tg-ws-proxy

- Образ tg-ws-proxy запинен по digest
  (`valnesfjord/tg-ws-proxy-rs:v2.5.8@sha256:d10285e7…`), а не по mutable-тегу
  `latest`: `docker compose pull` тянет ровно этот digest.
- Контейнер запускается с `read_only`, `cap_drop: ALL`,
  `no-new-privileges:true`, лимитами памяти/pids/CPU и ротацией логов;
  `env_file` — только `/etc/routeweave/.env.tgws`.
- Порт публикуется как `${SERVER_IP}:1443:1443`, а не на `0.0.0.0`. Docker
  при этом вставляет собственные правила в `DOCKER-USER`, которыми Routeweave
  не управляет: если `SERVER_IP` — публичный адрес или роутер пробрасывает
  `1443`, прокси будет доступен извне. Не пробрасывайте `1443` на роутере;
  полноценное ограничение `DOCKER-USER` отложено.

### Firewall и маршрутизация

- Вход на сам шлюз ограничивает цепочка `ROUTEWEAVE-IN` с прыжком в
  `INPUT 1`. Порядок: `lo` → `ESTABLISHED,RELATED` → ICMP → SSH (любая зона) →
  `INVALID DROP` → антиспуфинг CGNAT → разрешения для `53/tcp+udp`,
  `PANEL_PORT`, `9090`, `7890` (и `1443` при tg-ws) из `tailscale0`, `wdtt0`,
  `WG_SUBNET`, `TS_SUBNET`/`100.64.0.0/10`, а для LAN — только правилом с
  **двумя** условиями: `-i LAN_IFACE` и `-s LAN_CIDR` → `DROP` для этих портов
  из остальных источников → `RETURN`. Политика `INPUT` не меняется.
- `LAN_CIDR` — приватная подсеть(и) LAN через пробел/запятую; пусто =
  автоопределение из `LAN_IFACE`. Доверяются только RFC1918 (`10/8`,
  `172.16/12`, `192.168/16`): публичный или нулевой CIDR игнорируется с
  предупреждением и LAN-правила не добавляются. Если `LAN_IFACE` — единственный
  публичный NIC (VPS), установщик предупреждает об этом явно.
- `PANEL_BIND`, `MIHOMO_BIND` и `DNS_BIND` по умолчанию равны `SERVER_IP`:
  сервис не слушает прочие интерфейсы. `0.0.0.0` — осознанный opt-in, а не
  дефолт: в этом режиме сервис слушает все интерфейсы, и границей остаётся
  firewall (`ROUTEWEAVE-IN`). Для прямого доступа из tailnet задайте
  tailscale-адрес (безопаснее) или `0.0.0.0` при работающем `ROUTEWEAVE-IN`, а
  также `PANEL_ALLOWED_HOSTS`, `MIHOMO_API` и `MIHOMO_ALLOW_LAN=yes` для `7890`.
- Forwarding-правила живут в отдельной цепочке `ROUTEWEAVE-FWD`, из `FORWARD`
  в неё ведёт ровно один прыжок, и он проверяется, что стоит выше
  `ufw-before-forward`/`DOCKER-USER`. Это исключает конфликты позиций с
  docker/ufw.
- `DROP UDP/443` (`QUIC_DROP=yes`) стоит **выше** разрешающих правил, иначе
  QUIC у VPN-клиентов не режется. Трафик, помеченный `WAN_INGRESS_MARK`, из
  этого drop исключён: у опубликованных из WAN портов своя политика.
- `fw-base.sh` и `fw-wan.sh` используют `iptables -w 5`, а критичные ошибки
  валят юнит; если прыжок не удалось поставить выше чужих цепочек, firewall
  не считается применённым.
- `fw-wan.sh` на NEW-соединение ставит и метку пакета (`MARK`), и `CONNMARK`;
  `doctor` проверяет forwarded-путь помеченного пакета (от адреса клиента в
  `LAN_IFACE`, а не от `SERVER_IP`).
- `ip rule` priority 8990 направляет `WG_SUBNET` в таблицу маршрутизации
  Routeweave; VPN-интерфейсы (`wdtt0`, `tailscale0`, существующие `wg*`)
  получают ту же политику, что LAN.
- `TS_EXIT_MODE=nat` выводит трафик tailnet напрямую в WAN (MASQUERADE в
  `LAN_IFACE`), минуя geo/SOCKS/DPI-политику mihomo. Включать осознанно:
  в этом режиме к tailnet-трафику не применяются доменные правила и обход
  DPI; дефолт — `policy`. Схема DNS на `100.x.y.z:53` с fake-ip работает
  только в `policy`; в `nat` DNS уходит напрямую (NET-08).
- IPv6 осознанно не фильтруется: проект IPv4-only, `ip6tables` не трогается.
  `doctor` предупреждает об этом; IPv6 в LAN следует отключать.
- При активном ufw `install.sh` добавляет `ufw route allow in on LAN_IFACE` и
  `ufw allow from LAN_CIDR` только для приватного `LAN_CIDR`; для публичного
  или пустого CIDR — предупреждение, и эти правила не добавляются. Если
  `LAN_IFACE` — единственный публичный NIC, установщик предупреждает, что
  сервисы в LAN не открываются и доступ идёт через tailscale/WDTT/SSH-туннель.
- Наружу не пробрасываются `53`, `7890`, `9090`, `PANEL_PORT` и `1443`.
  Обещание обеспечено и на VPS, и при пробросе порта на роутере: LAN-разрешение
  требует одновременно `LAN_IFACE` и приватный `LAN_CIDR`, поэтому пакет из
  WAN (или с публичного адреса) под него не попадает. Bind по умолчанию на
  `SERVER_IP` (или loopback) уменьшает поверхность — сервис не слушает все
  интерфейсы, — но не заменяет firewall: на VPS `SERVER_IP` и есть публичный
  адрес, поэтому периметр держат правила `ROUTEWEAVE-IN` и Docker, а
  LAN-правило вдобавок требует приватный `LAN_CIDR`. Исключение — `56000/udp` для
  WDTT-Plus, он предназначен для внешнего доступа. `1443` — отдельный случай:
  его публикует Docker на `SERVER_IP`, и периметр держат правила Docker/ufw;
  не пробрасывайте `1443` на роутере.

Tailscale — отдельная граница доверия: доступ к панели и API mihomo по
tailscale-адресу регулируется ACL/grants и сроком действия ключей. Это не
публикация в интернет: `tailscale0` — интерфейс tailnet, а не проброс порта.
CGNAT-спуфинг (`100.64.0.0/10` не с `tailscale0`) дропается, а `41641/udp`
открыт только для прямых соединений Tailscale.

- Ключ авторизации Tailscale передаётся только на время установки:
  `TS_AUTHKEY_FILE` предпочтительнее; `TS_AUTHKEY` временно пишется в файл с
  правами `0600` и удаляется. В `/etc/routeweave/.env` и логи ключ не
  попадает.
- Уже авторизованный узел установщик не переустанавливает и не логинит
  заново: состояние `/var/lib/tailscale` сохраняется.
- Пакет Tailscale ставится из официального apt-репозитория — это отдельная
  граница доверия, как и другие внешние источники пакетов.
- DNS tailnet-клиентов на `100.x.y.z:53` с fake-ip работает только при
  `TS_EXIT_MODE=policy`; в `nat` трафик и DNS идут напрямую в WAN, доменные
  правила mihomo не применяются. Это известное ограничение (NET-08).

### Целостность загрузок (supply chain)

- Версии и sha256 зашиты в git и не берутся из mutable-источников: mihomo
  `v1.19.13` (отдельные суммы для `amd64-compatible`, `amd64`, `arm64`),
  zashboard `v3.29.1`, WDTT-Plus `v20` и zapret commit `c4d0b199…`.
- `verify_sha` требует ровно 64 hex и останавливает установку при
  несовпадении. `--allow-unverified`/`ALLOW_UNVERIFIED=yes` — только для
  отладки, громко предупреждает и не отключает проверку коммита zapret.
- Архивы zashboard и WDTT распаковываются в `mktemp`; симлинки, setuid,
  абсолютные пути и `..` отклоняются, затем выполняется атомарная замена
  каталога. Это защищает от подмены архива и выхода за пределы целевого пути.
- zapret собирается из закреплённого 40-hex commit. Ветка или тег в
  `ZAPRET_REF` — осознанный override с предупреждением; фактический `HEAD`
  всё равно сверяется и пишется в `/etc/routeweave/zapret.commit`.
- Домены списков проверяются по меткам; размер загрузки ограничен.
- Docker-образ tg-ws-proxy запинен по digest (см. раздел Docker), а
  `docker-compose.yml` проверяется в CI через `docker compose config`.

## Что не является уязвимостью

- Необходимость root для установки, изменения firewall и DNS.
- Доступ к панели по HTTP из доверенной LAN, если TLS не настроен: это
  известное ограничение с рекомендацией использовать reverse-proxy с TLS.
- Срезание QUIC при `QUIC_DROP=yes` и откат приложений на TCP — штатное
  поведение.
- Отсутствие фильтрации IPv6: проект IPv4-only, `ip6tables` осознанно не
  трогается. IPv6 в LAN нужно отключать.
- Публикация `1443` на `SERVER_IP`, если этот адрес публичный или роутер
  пробрасывает порт: это конфигурация Docker, а не обход firewall. Порт
  пробрасывать не нужно; ограничение `DOCKER-USER` отложено.
- Отсутствие защиты от пользователя, который уже является root на шлюзе:
  он по определению контролирует систему.
- Явный запуск с `--allow-unverified`/`ALLOW_UNVERIFIED=yes` — осознанный
  отказ от проверки sha256 архивов для отладки, а не дефект установщика.

## Ответственное раскрытие

Мы придерживаемся скоординированного раскрытия: 90 дней с момента
подтверждения отчёта либо иной срок по согласованию, если исправление
требует сложных изменений. Пожалуйста, не публикуйте детали и PoC до
выхода исправления. Указание автора в благодарностях — по желанию.
